# ProtrenerovKids.ru — стартовый бэкенд

Node.js + Express + PostgreSQL (Prisma ORM). Это не полный продакшн-бэкенд,
а рабочий каркас с уже реализованной бизнес-логикой, которую обсуждали
с заказчиком — разработчику останется подключить инфраструктуру
(реальный SMS-шлюз, VK ID, оплату) и доразвернуть остальные разделы
из общего ТЗ (`protrenerovkids-backend-tz.md`).

## Что уже реализовано и работает

**Файловое хранилище** (`services/storage/`) — абстракция + локальный
провайдер по умолчанию, тот же принцип, что у платежей и SMS. Фото тренера
(`POST /api/me/coach/photo`) — публичное, отдаётся статикой из
`/uploads/public`. Документы для верификации (`POST /api/me/coach/documents`)
— приватные, доступны только через аутентифицированные роуты (сам тренер и
менеджер, ведущий анкету). Проверка типа и размера файла, защита от path
traversal — 15 тестов на это, все проходят. Локальный диск не переживает
масштабирование на несколько серверов — см. `BLOCKED_EXTERNAL.md` (п. 10)
про переход на облачное хранилище, если до этого дойдёт.

**Важно про телефон тренера — два разных поля, не путать:**
- `Coach.phone` — внутренний, обязателен при создании анкеты, **никогда не
  публикуется** (нужен для связи и для разделения тренеров с одинаковыми
  ФИО — см. `routes/public/coaches.js`, где он всегда вырезается из ответа)
- `Coach.directContactPhone/Telegram/Max` — опциональные, публикуются
  только если тренер сам включил `bookingMode: "DIRECT_CONTACT"`

**Админка/менеджеры** (`/api/admin/*`):
- **Роли**: `MANAGER` и `SUPER_ADMIN` (`prisma/schema.prisma`, `middleware/auth.js`)
- **Менеджер видит только свои анкеты и звонки** — row-level scoping на уровне
  каждого запроса к БД, а не фильтрация на фронтенде (`middleware/roleScope.js`)
- **Защита от дублей анкеты**: жёсткая блокировка по телефону (в т.ч. когда
  один и тот же номер записан то через 8, то через +7) + мягкое предупреждение
  по совпадению ФИО+вида спорта (`lib/duplicateCheck.js`) — работает и когда
  анкету создаёт менеджер, и когда тренер сам меняет телефон в своём кабинете
- **Таблица обзвона** со статусами — менеджер выставляет их сам (`routes/callRecords.js`)
- **Комментарии к звонку — только добавление**, эндпоинтов на редактирование
  или удаление в API просто не существует
- **Claim-ссылка** (`lib/claimToken.js`): DRAFT → PENDING_CONSENT → VERIFIED,
  единственный переход, который делает сам тренер, а не менеджер/админ
- **Счётчик анкет менеджера** для расчёта оплаты (`routes/managerStats.js`)
- **Удаление/редактирование отзывов и разбор жалоб — только SUPER_ADMIN**
  (`routes/reviews.js`), архивация анкет — тоже только SUPER_ADMIN (`routes/coaches.js`)
- **Заявки на новый вид спорта**: список + одобрение с автосозданием анкеты
- **Клики по прямому контакту** (телефон/Telegram/MAX) — публичный
  эндпоинт считает клики, админка сортирует анкеты по популярности
  (`?sortBy=clicks`) или смотрит топ отдельным списком (`/top-by-clicks`)
  (`routes/sportRequests.js`)
- **Журнал действий** (`AuditLog`) — выгрузки, удаления отзывов, разбор жалоб

**Публичная часть сайта** (без авторизации, `routes/public/*`):
- Каталог тренеров с фильтрами, публичный профиль (без внутреннего телефона/документов)
- Заявка на запись (форма) с обязательным согласием и логированием в `Consent`
- Отзыв → SMS-код → подтверждение → пересчёт рейтинга и счётчика для геймификации
- Арены, спортшколы, заявка на новый вид спорта, приглашение тренера
- **Подтверждение claim-ссылки тренером** (`routes/public/claim.js`) — раньше
  функция `confirmClaim()` существовала, но ни один HTTP-роут её не вызывал,
  тренер физически не мог подтвердить анкету по ссылке из SMS. Исправлено.

**Вход по SMS-коду** (`routes/auth.js`) — единый флоу для тренера и
менеджера/супер-админа, кто именно логинится определяется по совпадению
номера после подтверждения кода, не выбором на фронте:
- `lib/otpStore.js` — общее хранилище кодов (TTL 5 минут, до 5 попыток,
  затем код гасится), используется и здесь, и при подтверждении отзыва.
  Раньше подтверждение отзыва держало код в отдельном `Map` без очистки —
  записи росли бесконечно, теперь оба места используют один модуль с
  автоочисткой
- `lib/smsProvider.js` — абстракция, как и у платежей; мок печатает код в
  консоль сервера, реальный провайдер не выбран (см. `BLOCKED_EXTERNAL.md`)
- `lib/captchaProvider.js` — Yandex SmartCaptcha, реализовано по проверенной
  актуальной документации, без ключа в `.env` пропускается только в деве
- VK ID — честная заглушка (`501`, не `404`), точные эндпоинты современного
  VK ID не подтвердились по доступным источникам при поиске — решил не
  додумывать, см. `BLOCKED_EXTERNAL.md`

**Кабинет тренера** (`/api/me/*`, вход по SMS/VK ID — `middleware/coachAuth.js`):
- Своя анкета (белый список полей — тренер не может сам себе проставить
  `status` или `documentsVerified` через общий PUT), публикация, заявки,
  дневник тренировок, ответы на отзывы
- **Подписка «Прямой контакт» через настоящую модель `Subscription`/`Payment`**
  (не плоские поля на `Coach`) — разделены понятия recurring permission,
  успешный/неудачный платёж, отмена, возврат (см. `prisma/schema.prisma`).
  `Coach.isPremium` — денормализованная проекция, которую пересчитывает
  только `lib/entitlement.js`, больше нигде это поле не пишется напрямую
- **Платёжный провайдер — абстракция + мок** (`lib/paymentProvider.js`).
  Конкретный адаптер (ЮKassa/Точка/Альфа-Банк) не выбран — см.
  `BLOCKED_EXTERNAL.md`, там же порядок действий после выбора
- **Отмена подписки** (`POST /api/me/premium/cancel`, `lib/subscriptionCancel.js`)
  — первые 3 дня с последней оплаты полный возврат (по-настоящему вызывает
  `provider.refund()` и не подтверждает возврат, если провайдер его не
  подтвердил), позже оплаченный период донашивается, автопродление
  выключается. 3 дня — решение бизнеса, не требование закона, обязательно
  продублируйте эту же формулировку в публичной оферте
- **Вебхук платежа устроен так, что одно успешное списание = один
  оплаченный период** — `subscription.created` сам по себе период не
  продлевает (раньше здесь был баг двойного начисления, если оба события
  приходят на один и тот же первый платёж — исправлено)
- Автоматическое отключение по истечении "донашиваемого" периода — теперь
  не просто скрипт для ручного cron, а постоянный воркер `src/worker.js`
  (`npm run worker`), restart-safe и защищён от наложения двух запусков
  подряд; `scripts/deactivateExpiredPremium.js` остаётся как вариант для
  внешнего OS-level cron — оба используют одну и ту же идемпотентную job
- **PDF-документы по записи** (`GET /api/me/bookings/:id/documents/:type`,
  `lib/pdfGenerator.js`) — технический генератор на `pdf-lib` с проверкой
  владения (чужой booking → `404`). Текст — фикстура-плейсхолдер, финальные
  юридические формулировки и шрифт с кириллицей — см. `BLOCKED_EXTERNAL.md`
- Обработка фото — заглушка с понятной точкой подключения

**Всё это покрыто ручными функциональными тестами**
(`src/lib/__tests__/*.manual-test.js`) — запускаются без БД, на фейковых
данных в памяти, уже нашли и исправили один реальный баг
(нормализация телефона).

## Что добавлено сверху, чтобы разработчику было легче

Дальше — вещи, которые обычно всплывают только в проде и стоят разработчику
отдельного дня отладки, если не заложены заранее:

- **`docker-compose.yml`** — поднимает Postgres одной командой
  (`docker compose up -d`), не нужно ставить и настраивать локально
- **`.gitignore`** — раньше отсутствовал; без него `.env` с реальными
  паролями мог случайно уйти в репозиторий
- **Единая обработка ошибок** (`express-async-errors` + middleware в конце
  `src/index.js`) — без этого ошибка Prisma внутри `async`-роута просто
  зависала бы без ответа клиенту, вместо понятного кода ошибки
- **CORS** и **rate limiting** на всём, что шлёт SMS или создаёт записи
  без авторизации (иначе таблицу отзывов можно забить скриптом за секунды)
- **Валидация входных данных** через `zod` (`src/lib/validation.js`) —
  теперь подключена **ко всем** POST/PUT/PATCH-эндпоинтам проекта, не только
  к трём основным; 20 тестов на схемы валидации, все проходят
- **`SMS_TEMPLATES.md`** — готовые тексты всех SMS-сообщений (коды подтверждения,
  уведомления тренеру и родителю, модерация) с пояснениями по длине сегмента
  и юридическими примечаниями там, где это важно
- **`protrenerovkids.postman_collection.json`** — 39 запросов, сгруппированных
  по разделам из `API.md`, с примерами тел запросов и переменными для токенов —
  импортируется в Postman/Insomnia одним файлом, тестировать можно кликами,
  не вспоминая curl
- **`TODO.md`** — все `TODO(разработчик)` из кода собраны в один
  приоритизированный список (🔴 блокирует запуск / 🟡 частично работает /
  🟢 можно после запуска), не нужно искать по всему проекту
- **Пагинация** на всех списочных эндпоинтах (`src/lib/pagination.js`) —
  иначе один запрос к каталогу тренеров однажды вернёт мегабайты JSON
- **Индексы БД** на полях, по которым реально фильтруют (статус жалобы,
  связка статус+вид спорта+рейтинг в каталоге) — без них Postgres будет
  делать полное сканирование таблицы на каждый запрос к каталогу
- **Заготовка вебхуков** (`src/routes/webhooks.js`) с проверкой HMAC-подписи —
  нашла и исправила реальный баг по ходу: платёжный вебхук требует "сырое"
  тело запроса для проверки подписи, а порядок middleware в `index.js`
  был бы неправильным (global `express.json()` съел бы тело раньше)
- **CI** (`.github/workflows/ci.yml`) — синтаксис-чек и все тесты гоняются
  на каждый push/PR. Заодно нашла, что тесты печатали ❌, но не завершались
  с ошибкой — CI бы не заметил падение. Все файлы тестов используют
  общий помощник (`testHelper.js`) с правильным exit-кодом
- **`src/lib/tokens.js`** — форма JWT-токена определена в одном месте,
  а не продублирована между заглушкой логина и seed-скриптом
- **`API.md`** — построчно сверен с реальным кодом маршрутов (не написан
  «по памяти»)

## Что нужно доделать разработчику

1. **Вход по SMS / VK ID** — сейчас в `POST /api/auth/verify-code` только
   заглушка с комментарием, что и куда подключать; форма токена уже готова
   в `src/lib/tokens.js`
2. **Внешние интеграции** — везде, где в коде `// TODO(разработчик)`:
   SMS-провайдер, VK ID OAuth, remove.bg/Photoroom, генерация PDF,
   Telegram-бот, платёжный провайдер (СБП через Точка/Альфа-Банк/ЮKassa —
   именно эти работают с самозанятыми, в отличие от Т-Банк/CloudPayments)
3. **SMS-шлюз** — тексты уже готовы (`SMS_TEMPLATES.md`), нужно только подключить
   провайдера и вызвать нужный шаблон в местах с `// TODO(разработчик)`
4. **seed-скрипт** (`prisma/seed.js`) готов, но `npm install` разработчику
   всё равно нужно прогнать самому — в этой среде нет доступа в npm-реестр

## Запуск

```bash
docker compose up -d    # поднимает Postgres локально
cp .env.example .env    # уже готов под docker-compose как есть, поменяйте JWT_SECRET
npm install
npx prisma migrate dev --name init
npm run prisma:seed     # тестовые данные + JWT-токены для ручной проверки
npm run dev
```

После этого сайт открывается прямо на `http://localhost:3000/` — фронтенд
(`public/index.html`) отдаётся тем же процессом, что и API, отдельный
сервер под статику не нужен. `public/index.html` — копия файла из
`01-frontend-maket/` в пакете для передачи; при обновлении макета копию
нужно обновлять вручную (эти два файла не связаны автоматически).

Если предпочитаете разместить фронтенд отдельно (например, на статическом
хостинге) — это тоже сработает, тогда в `public/index.html` поменяйте
`API_BASE_URL` на полный адрес бэкенда и убедитесь, что `CORS_ORIGIN` в
`.env` указывает на домен, откуда фронтенд реально будет открываться.

## Как проверить логику руками (без БД и без запуска сервера)

```bash
node src/lib/__tests__/duplicateCheck.manual-test.js
node src/lib/__tests__/claimToken.manual-test.js
```

Оба скрипта гоняют реальную бизнес-логику на фейковой базе в памяти —
никакого Postgres для этого не нужно. Разработчику стоит держать эту
практику и для новых модулей: писать такой же лёгкий тест рядом с кодом.

## Как проверить остальное руками (уже после запуска и настройки БД)

Без готового /login можно вручную выдать себе тестовый JWT для проверки —
разработчик обычно делает для этого небольшой seed-скрипт
(`prisma/seed.js`), создающий одного SUPER_ADMIN и одного MANAGER
с уже готовыми токенами для локальных тестов.

Или ещё проще — импортировать `protrenerovkids.postman_collection.json` в
Postman/Insomnia, вставить токены из вывода `npm run prisma:seed` в
переменные коллекции (`superAdminToken`, `managerToken`, `coachToken`)
и тестировать все 48 запросов кликами.
