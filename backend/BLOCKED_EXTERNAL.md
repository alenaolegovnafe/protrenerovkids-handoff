# Заблокировано внешними факторами

Список того, что технически НЕ реализовано (или реализовано только как мок/
заглушка) потому, что реализация зависит от решения заказчика, доступа к
внешнему сервису или документа, которого пока нет. Всё остальное в проекте
считать полностью реализованным и протестированным — этот список закрытый,
не "на всякий случай".

## 1. Платёжный провайдер

**Статус:** абстракция + мок-провайдер готовы (`src/lib/paymentProvider.js`,
`src/routes/webhooks.js`, `src/lib/subscriptionCancel.js`). Конкретного
внешнего адаптера нет.

**Почему заблокировано:** заказчик обсуждал Точка / Альфа-Банк / ЮKassa
(самозанятая, нужна поддержка СБП-подписок без ИП), но не выбрал и не
подключил ни одного. Формат webhook-события, API возврата, создания
подписки — у каждого провайдера свой, додумывать по аналогии не стал.

**Что нужно сделать после выбора провайдера:**
1. Изучить АКТУАЛЬНУЮ официальную документацию выбранного провайдера.
2. Создать `src/lib/providers/<name>Provider.js` с тем же набором методов,
   что и `mockProvider` в `paymentProvider.js` (`createRecurringPermission`,
   `cancelRecurring`, `refund`, `verifyWebhookSignature`).
3. Добавить его в `getPaymentProvider()`.
4. Проверить реальный формат вебхук-события провайдера и при необходимости
   поправить парсинг в `routes/webhooks.js` (сейчас там предполагаемая форма
   `{ id, type, coachId, providerSubscriptionId, providerPaymentId, amountRub }`).
5. Установить `PAYMENT_PROVIDER=<name>` и `PAYMENT_WEBHOOK_SECRET` в `.env`.

## 6. VK ID

**Статус:** секьюрити-обвязка есть (`GET /api/auth/vk/callback` возвращает
понятный `501`, не 404), но сам обмен кода на токен НЕ реализован —
`lib/vkIdProvider.js` явно бросает ошибку с объяснением, почему.

**Почему заблокировано:** VK ID — современный продукт (не путать со старым
VK OAuth на `oauth.vk.com`, у него другие домены и обязательный PKCE-флоу).
Поиск актуальной документации не дал уверенного результата — источники
оказались смесью устаревших ответов про старый OAuth и разрозненных
обрывков без полной картины по текущему VK ID. Додумывать точные
URL/параметры не стал — по методологии проекта явная заглушка лучше кода,
который выглядит рабочим, но использует непроверенные детали.

**Что нужно сделать:**
1. Зарегистрировать приложение в VK ID for Business, получить client_id/secret.
2. Свериться с ТЕКУЩЕЙ официальной документацией VK ID (адрес мог измениться
   с момента подготовки этого файла — искать "VK ID for Business docs").
3. Реализовать `exchangeVkCode()` в `lib/vkIdProvider.js` реальным вызовом
   по документации, включая PKCE (code_verifier/code_challenge) — этого
   требует именно VK ID, в отличие от старого VK OAuth.
4. Доделать роут `GET /api/auth/vk/callback` в `routes/auth.js` — обменять
   код, получить телефон пользователя (если VK ID его отдаёт с нужным
   scope), найти/связать с Coach/AdminUser по номеру, выдать токен так же,
   как в `/api/auth/verify-code`.

## 7. Yandex SmartCaptcha

**Статус:** реализовано полностью (`lib/captchaProvider.js`), эндпоинт и
формат запроса подтверждены по официальной документации Yandex Cloud
(`POST https://smartcaptcha.yandexcloud.net/validate`). Без ключа в `.env`
проверка пропускается с явным предупреждением в консоли — это нормально
для дева, но **обязательно задать `YANDEX_CAPTCHA_SECRET` перед продом**,
иначе форма запроса кода останется без защиты от ботов.

**Что нужно:** завести капчу в консоли Yandex Cloud (SmartCaptcha), получить
`server_key` и `client_key`, `client_key` передать фронтенду для отрисовки
виджета, `server_key` — в `.env` как `YANDEX_CAPTCHA_SECRET`.

## 9. Формулировка возврата в публичной оферте

**Статус:** юрист (не разработчик) отметил, что для потребительских
отношений закон может требовать более широкий пропорциональный возврат за
неиспользованный период, чем реализованное правило "3 дня — полный возврат,
позже — без возврата". Само правило технически реализовано и работает
именно так, как описано в UI и в `subscriptionCancel.js` — вопрос в том,
достаточно ли этого юридически. Не блокирует запуск технически, но перед
запуском стоит получить финальное подтверждение от юриста.

## 10. Файловое хранилище — облако для масштабирования

**Статус:** реализовано полностью для запуска на одном сервере
(`services/storage/localProvider.js`) — загрузка фото тренера и документов
для верификации работает по-настоящему, с проверкой типа/размера файла и
защитой от path traversal (15 тестов, все проходят).

**Почему всё-таки в этом списке:** локальный диск не переживает
горизонтальное масштабирование (несколько инстансов сервера за
балансировщиком — каждый видел бы только свою часть файлов) и не
переживает передеплой на платформах без постоянного смонтированного тома
(часть PaaS-хостингов стирают диск при каждом деплое).

**Что нужно сделать, если проект вырастет за один сервер:**
1. Выбрать облачное объектное хранилище — для российского хостинга
   разумные варианты: Yandex Object Storage или VK Cloud Storage
   (оба S3-совместимы).
2. Создать `src/services/storage/providers/<name>Provider.js` с тем же
   набором методов, что и `localProvider.js` (`save`, `remove`,
   `getPublicUrl`, `getAbsolutePath` — для приватных файлов вместо
   абсолютного пути с диска потребуется возвращать способ их прочитать,
   например presigned URL с коротким сроком жизни).
3. Добавить его в `getStorageProvider()` (`services/storage/index.js`) и
   переключить `STORAGE_PROVIDER` в `.env`.
4. Существующие файлы на локальном диске придётся перенести в облако
   отдельным скриптом-миграцией — это не сделается само.

## 11. Резервное копирование базы данных

**Статус:** не настроено вообще — этого нет ни в каком виде, и это не то,
что можно "написать кодом" без реального сервера, на котором это
разворачивается.

**Что нужно сделать при реальном запуске:** большинство managed-хостингов
PostgreSQL (Yandex Managed PostgreSQL, VK Cloud DB и т.п.) включают
автоматические резервные копии "из коробки" — обычно это просто галочка в
настройках при создании базы, а не что-то, что нужно программировать. Если
база разворачивается на своём сервере вручную — нужен `pg_dump` по
расписанию (cron) с выгрузкой в отдельное хранилище (не на тот же диск,
где сама база — иначе один и тот же сбой диска убьёт и базу, и бэкапы).

## 12. Мониторинг ошибок в проде

**Статус:** тоже не настроено. Сейчас все ошибки на сервере просто пишутся
в консоль (`console.error`) — при реальном запуске это означает, что
разработчик узнает о поломке только если сам зайдёт посмотреть логи.

**Что нужно сделать:** подключить сервис вроде Sentry (есть бесплатный
тариф) — несколько строк кода в `index.js` для перехвата необработанных
ошибок и отправки их разработчику/в чат. Не блокирует запуск технически,
но без этого поломки будут замечены только по жалобам пользователей.

## 13. Каталог фильтрует только фигурное катание и хоккей

**Статус:** осознанная граница MVP, а не забытая недоделка — сайт изначально
заявлен под эти два вида спорта, и вся система фильтров, значков и
специфичных для вида спорта полей построена вокруг них двоих.

**Что это значит на практике:** если через «Заявки на новые виды спорта»
одобрить тренера, например, по плаванию — анкета технически создастся и
опубликуется корректно (это уже реализовано и работает, включая SMS
тренеру), но новый вид спорта **не появится** как отдельный пункт в
фильтре каталога — такую анкету можно будет найти только через общий
поиск, не через выбор вида спорта.

**Что нужно сделать, если решите расширяться на другие виды спорта:**
это отдельная, не маленькая задача — фильтр каталога, значки на карточках,
поля, специфичные для конкретного спорта (сейчас есть только
`hockeyStickType` для хоккея) нужно продумывать заново под каждый новый
вид спорта, а не один раз обобщить.

## 14. Право отказать тренеру в удалении анкеты из-за плохих отзывов

**Статус:** технически анкета архивируется, а не удаляется физически
(`status: ARCHIVED`) — сами данные и отзывы сохраняются. Но закреплено ли
это как ПРАВО оператора именно отказать в удалении по такой причине — не
подтверждено юристом.

**Что нужно уточнить у юриста:** отзывы клиентов — это отдельные
персональные данные (согласие клиента, не тренера), и вопрос "может ли
тренер потребовать удаления своей анкеты, чтобы избавиться от плохой
репутации" пересекается с правами других субъектов (клиентов, оставивших
отзывы) и с защитой интересов будущих клиентов (родителей). Стоит явно
прописать в пользовательском соглашении, на каком основании площадка
вправе не удалять анкету/отзывы по первому требованию — сейчас в
документах эта ситуация отдельно не описана.

**Что уже сделано технически** (см. `lib/duplicateCheck.js`): при попытке
завести новую анкету тренеру, чья предыдущая анкета в архиве, менеджер
получает явное предупреждение — по совпадению телефона или похожего ФИО.
Дополнительно при загрузке документов сверяется содержимое файла (хеш) —
если тот же самый диплом/сертификат всплывает у другой анкеты (в том числе
архивной), это тоже отмечается для проверки администратором. Ни один из
этих механизмов не блокирует автоматически — оба только предупреждают,
окончательное решение остаётся за менеджером/супер-админом.
